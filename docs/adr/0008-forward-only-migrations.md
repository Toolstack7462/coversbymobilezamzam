# ADR 0008 — Forward-only migrations, never `push`

**Status:** Accepted · 2026-08-30

## Context

The database holds orders, payments and inventory — data that cannot be
regenerated. Schema changes will keep coming. Drizzle Kit offers both `generate`
(write a migration file) and `push` (diff the live schema and apply it directly).

## Decision

Forward-only SQL migration files in `db/migrations`, generated by
`drizzle-kit generate`, committed, reviewed, and applied with
`wrangler d1 migrations apply`.

**`drizzle-kit push` is never run against any deployed database.** No `db:push`
script exists in `package.json` — the easiest way not to run a dangerous command
is not to have it.

No down-migrations. Recovery is restore-from-backup plus a corrective forward
migration.

## Alternatives considered

**`push` for speed.** Genuinely convenient in development. Rejected because it
infers a diff at deploy time and applies it with no review artefact. A renamed
column reads as drop-plus-add; a narrowed type reads as a rewrite. Against a
table of real orders that is unrecoverable, and nothing in the process would have
shown a human what was about to happen.

**Down-migrations.** The conventional answer. Rejected as a comfortable fiction:
a down-migration for "drop column" cannot restore the data it dropped. Believing
rollback is available encourages riskier forward changes. Restore-plus-fix is
honest about what is actually possible.

**An ORM that auto-syncs at boot.** Rejected: schema changes must not happen as a
side effect of a deploy.

## Consequences

**Good.** Every schema change is a reviewable artefact in git. What runs in
production is the file that was reviewed. Migration state is queryable.
Integration tests apply the same files, so a broken migration fails CI rather
than production.

**Bad.** More steps in development. Renames are two steps (add, backfill, drop)
rather than one. There is no one-command undo.

**Mitigations.** `npm run db:generate` after every schema edit.
`npm run migrations:check` fails if schema and migrations diverge. A backup is
mandatory before any `--remote` apply. Additive changes are preferred so that
most releases need no destructive step at all.

## Rollback

Restore from the pre-migration backup, then write a corrective forward migration.
The procedure, including how to verify a restore actually worked, is in
`docs/backup-and-restore.md`.
